# Delta for Retrieval (GraphRAG)

## MODIFIED Requirements

### Requirement: Authoritative Cypher template
The traversal layer SHALL execute **only** Cypher templates registered
in the Cypher Template Catalogue (`assets/cypher/catalog.yaml`). Each
registration MUST bind:

- a stable `intent_id`,
- the template file path,
- a typed parameter contract (name, type, required),
- a flag declaring whether the template is bitemporal-aware,
- at least one golden test case under `assets/cypher/tests/golden/`.

Free-form Cypher generated by the LLM is forbidden for production
queries. The executor MUST reject:
1. any `intent_id` not present in the catalogue,
2. any parameter set that does not satisfy the manifest contract,
3. any attempt to pass a Cypher string in place of an `intent_id`.

Adding, removing, or modifying a template MUST happen via an
OpenSpec change that updates `catalog.yaml`, the `.cypher` file, and
the golden tests in the same PR.

#### Scenario: Unregistered intent rejected
- GIVEN the API receives a request mapped to `intent_id=premium_rollup`
- AND `premium_rollup` is not in `catalog.yaml`
- WHEN the executor runs
- THEN the request MUST be rejected with `unknown_intent`
- AND no Cypher is sent to Neo4j.

#### Scenario: Parameter contract enforced
- GIVEN template `coverage_judgment` declares `party_id: string`
        (required)
- WHEN the executor is invoked with `party_id=42` (integer)
- THEN the executor MUST refuse with `parameter_type_mismatch`
- AND no Cypher is sent to Neo4j.

### Requirement: Exclusion / coverage precedence (layered)
When clauses of the same active policy disagree about a `RiskPeril`,
the answerer SHALL resolve the verdict by the following layered
precedence (highest first):

| Layer | Source                                              |
|------:|-----------------------------------------------------|
| L1    | An `Endorsement` that INTRODUCES reinstated coverage|
| L2    | A `Rider` product clause that COVERS the peril      |
| L3    | A base-product `:EXCLUDES` clause                   |
| L4    | A base-product `:COVERS` clause                     |

Within the same layer, ties break by `recorded_at DESC`. The answer
payload MUST surface every clause that participated in the conflict
and the layer that won.

#### Scenario: Rider reinstates excluded peril
- GIVEN base product excludes peril `PER_AMI` via clause `CL_BASE_EXC`
- AND a rider product attached via `[:RIDES_ON]` covers `PER_AMI` via
        clause `CL_RIDER_COV` on the same active policy
- WHEN the user asks whether `PER_AMI` is covered
- THEN the verdict MUST be `COVERED`
- AND `resolution_layer` MUST be `L2`
- AND both `CL_BASE_EXC` and `CL_RIDER_COV` MUST appear in
       `conflicting_clauses` with their respective layers.

#### Scenario: Pure base-product conflict
- GIVEN peril P is covered by clause CA and excluded by clause CB on
        the base product (no rider, no endorsement)
- WHEN the user asks whether P is covered
- THEN the verdict MUST be `EXCLUDED`
- AND `resolution_layer` MUST be `L3`
- AND `CB` MUST be cited.

## ADDED Requirements

### Requirement: Intent disambiguation
The retrieval layer SHALL classify each user question to a single
`intent_id` in the catalogue. When the top-2 intent candidates are
within 0.05 score of each other, the API MUST return a structured
`clarification` payload listing the candidate intents and the
disambiguating questions, rather than guessing.

#### Scenario: Ambiguous question triggers clarification
- GIVEN a user asks "保单到期日是什么时候?" while the catalogue
        contains both `policy_term_lookup` and `claim_status_lookup`
- AND the classifier produces scores `0.51` and `0.48`
- WHEN the API processes the question
- THEN the response is a `clarification` payload
- AND no template is executed.
